HF_Locking: Windows Focus-Throttling Fix and GUI Rate Audit

Date: 2026-05-05  •  Commit: pending  •  Context: Wavemeter GUI felt laggy/jittery when window lost focus; fixed at OS, process, and timer layers, then audited GUI refresh cadences.

What Changed

Diagnosed and fixed focus-induced UI lag in the HighFinesse wavemeter GUI (GUIs/HF_Locking/main_wlm.py). Root cause was Windows 11 EcoQoS throttling unfocused processes (CPU clock reduction + E-core migration), not process priority. Fix is process-wide opt-out via SetProcessInformation(ProcessPowerThrottling). Also demoted the priority class from HIGH to ABOVE_NORMAL (better fit for a continuous polling loop), tightened the GUI fast timer to PreciseTimer, and aligned the GUI slow rate (1 Hz) with its 1 Hz worker producer. New docs/hf-locking-rates.md inventories every continuous and event-driven rate in the GUI with rationale.

Key Decisions

EcoQoS opt-out is the real fix, not priority elevation. On Win10 1709+ / Win11, the OS throttles unfocused processes by reducing CPU execution speed and shifting them to efficiency cores. This is independent of PriorityClass. Disable per-process via: 
state.Version     = 1
state.ControlMask = 0x1   // EXECUTION_SPEED
state.StateMask   = 0     // 0 with mask set => disable
SetProcessInformation(handle, ProcessPowerThrottling=4, &state, sizeof(state))
Process-wide, so worker threads inherit it. Does not require admin.
ABOVE_NORMAL is the correct default for continuous-polling Python in this lab. Microsoft's Scheduling Priorities doc explicitly reserves HIGH for brief time-critical events, not 20 ms continuous loops. Sustained HIGH (base 13) risks starving disk / USB / audio system threads which sit at base 8-12. ABOVE_NORMAL (base 10) still beats NORMAL plus the foreground-priority boost (which only acts on NORMAL-class processes), and does not require admin.
Per-EXE powercfg /powerthrottling disable is the closed-source equivalent. For the HighFinesse server (wlm_ws7.exe) we cannot patch source, so the per-EXE rule is the equivalent OS-level opt-out. Persists across reboots; may be wiped by major Windows feature updates. 
powercfg /powerthrottling disable /path "C:\Program Files (x86)\HighFinesse\Wavelength Meter WS7 8407\wlm_ws7.exe"

Patterns Observed

  • windows Two independent throttling axes on Win11: priority class (CPU scheduler) and EcoQoS / power throttling (clock + core selection). Fixing one does not address the other. Both should be considered for any latency-sensitive Python lab tool on Windows.
  • brainstorm Brainstorming skill workflow worked well for the rate audit: single-question clarifying loop → three approaches with recommendation → spec write → self-review → user-confirm before executing. Reuse for multi-knob audits.
  • honesty Concrete failure-mode framing ("PreciseTimer helps narrowly: cycle-shift wrap, system contention") landed better than overselling. Be candid about marginal benefits.

Regression & Resolution (2026-05-06)

The CoarseTimer → PreciseTimer change for _gui_timer_fast caused a complete GUI freeze at launch on Win11. Main window painted via show() but the Qt main thread never pumped events — clicking surfaced "Not Responding". Both [PRIORITY] and [POWER] startup lines printed (the EcoQoS opt-out and priority demotion ran fine); no _RestoreDialog appeared (ruling out the modal hypothesis). Bisected to a single line: reverted Qt::PreciseTimer back to Qt::CoarseTimer at main_wlm.py:236 — GUI launched and responded normally. The other three changes from this commit (EcoQoS opt-out, ABOVE_NORMAL priority, GUI_SLOW_MS = 1000) are kept; they were correct.

Mechanism (best-supported, not bench-verified)

On Windows, Qt's PreciseTimer uses the Multimedia Timer API (timeSetEvent), which fires events from a separate kernel thread on a 1 ms-resolution heartbeat (timeBeginPeriod(1)) and posts them into the target thread's message queue without the natural rate-limiting that WM_TIMER/SetTimer has. CoarseTimer uses SetTimer, where the message pump itself naturally drops/coalesces late WM_TIMER messages. Even though Qt docs assert that both timer types coalesce late timeout() signal emissions (so coalescing-failure is not the mechanism), the underlying message-pump backpressure differs by backend. Combined with: (i) the GUI's _refresh_gui_fast triggering 8 channels × pyqtgraph setData = ~16-48k point updates per frame, plausibly >33 ms total per call; (ii) the unthrottled (EcoQoS-off, ABOVE_NORMAL) worker thread contending the GIL at 50 Hz — paint/input events get starved enough for Windows to mark the window unresponsive.

Rule (added to docs/hf-locking-rates.md)

  • Default CoarseTimer for any QTimer that drives heavy work on the Qt main thread.
  • Reserve PreciseTimer for worker QThreads and hardware-sync loops where missing a tick has hardware consequences.
  • The PreciseTimer benefit (cycle-shift wrap stutter going from ±5-15 ms jitter to ±1 ms) is a one-shot ~14 ms visual hiccup once per sweep period — not worth the multimedia-timer fragility.
  • If plot smoothness ever actually matters, tune per-frame work (decimate plot buffers to ~100 visible points, partial updates only on changed channels, useOpenGL=True), not timer precision.
