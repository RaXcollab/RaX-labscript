Rastering Audit: Race Condition Fix + PUB-SUB Monitor Reads

Date: 2026-03-06  •  Commit: pending  •  Context: Audit of rastering GUI and BLACS device; fixed race condition and migrated monitor reads to PUB-SUB

What Changed

Audited the rastering system end-to-end (GUI controller + BLACS device). Found and fixed a race condition in the raster point enqueue logic where stop_raster() could run between the active-check and next(iterator), causing a spurious point after stop. Also added a guard against starting a raster without calibration. On the BLACS side, replaced REQ-REP round-trips for monitor value snapshots with reads from a PUB-SUB cache shared between tab and worker, and added a post_experiment() override to save initial+final monitor values to h5.

Bugs Found & Fixed

Race condition in _enqueue_next_raster_point()
The lock was released after checking _raster_active but before calling next(iterator). If stop_raster() ran in that window (common with QTimer.singleShot delays), the iterator could be consumed after stop, enqueuing a spurious move command. Fix: hold lock through both the check and the next() call. StopIteration is caught inside the lock; _finish_raster() is called outside (it emits signals that must not be under the lock).
Missing calibration guard in start_raster()
No check prevented starting a raster when self.calibration was None. Downstream code would crash on NoneType. Fix: early return with status message.

Key Decisions

  • PUB-SUB for reads, REQ-REP for writes. Consistent with BigSkyHub and LaserLockDevice patterns. Monitor values update at ~4 Hz via the subscriber thread. Motor has settled by the time program_manual() runs, so cached values are accurate.
  • Shared dict reference (tab → worker). Tab and worker run in the same process. Passing the dict via init_kwargs gives the worker a live reference. No extra ZMQ needed.
  • try/except StopIteration inside lock, _finish_raster() outside. _finish_raster() emits Qt signals and acquires its own lock. Calling it inside the existing lock acquisition would either deadlock (non-reentrant) or cause signal ordering issues.
  • Uncalibrated guard is soft (status message + return), not an exception. Consistent with GUI UX pattern — user sees feedback, nothing crashes.
