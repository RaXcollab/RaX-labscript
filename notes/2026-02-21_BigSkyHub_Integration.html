BigSkyHub — BLACS Integration for YAG Laser Control

Date: 2026-02-21  •  Commit: pending  •  Context: New BLACS device class for BigSky YAG laser control via RemoteControl ZMQ protocol

What Changed

Created BigSkyHub device class in userlib/user_devices/BigSkyHub/ to interface BLACS with the Big Sky YAG laser control GUI. The device subclasses RemoteControl and auto-creates 28 channels (9 writable outputs + 5 read-only monitors per laser, for 2 lasers). The critical addition is a worker override that enforces safe command ordering during buffered shots, preventing the BigSky server's safety interlocks from rejecting out-of-order commands.

Key Decisions

1. Subclass vs. direct use of RemoteControl

Subclassing was required because the base RemoteControlWorker.transition_to_buffered iterates HDF5 columns in arbitrary (dtype) order. The BigSky server has safety interlocks: e.g., opening the shutter before lamps are active is rejected. The worker override groups channels by laser prefix and sorts by a COMMAND_ORDER dictionary.

2. Auto-creation of children

Unlike RasteringDevice (where each RemoteAnalogOut / RemoteAnalogMonitor is declared manually in the connection table), BigSkyHub auto-creates all 28 children in its __init__. Rationale: every BigSky laser always has exactly the same 9 outputs and 5 monitors — there is no reason to require 14 manual declarations per laser. This reduces the connection table entry from ~30 lines to 1 line.

Pattern note: The auto-creation approach should be considered for any future RemoteControl subclass where the channel set is fixed. It could be backported to RasteringDevice (which always has exactly X/Y output + X/Y monitor).

3. Minimal tab override

BigSkyTab inherits the entire RemoteControlTab GUI (auto-generated spinboxes for all outputs and monitors). The only override is initialise_workers(), which points to BigSkyWorker instead of RemoteControlWorker. No custom widgets needed — the 28 spinboxes are generated automatically from the child connections.

Command Ordering (Safety Critical)

The BigSkyWorker.transition_to_buffered method enforces this order for each laser:

PriorityCommandRationale
0stopEnsure standby before any mode changes
1qswitch_modeMode change requires standby state
2lamp_modeMode change requires standby state
3voltageSet voltage before activating hardware
4lampsActivate flashlamps (voltage must be set)
5shutterRequires lamps active
6qswitchRequires lamps + shutter active
7warmupCompound command, sent last
8start_lasingCompound command, sent last
Safety: If commands are sent out of order, the BigSky server will reject them and BLACS will raise an exception during transition_to_buffered. This is by design — the server enforces interlocks to prevent laser damage. The COMMAND_ORDER dict in blacs_workers.py must stay synchronized with the server's interlock logic.

How to Use

  1. Start the BigSky YAG control GUI (it binds REP on port 55540, PUB on 55541)
  2. Start BLACS — the BigSkyHub tab appears with 28 spinboxes (18 outputs, 10 monitors)
  3. Manual control: Use spinboxes directly. Each change sends a PROGRAM_VALUE to the BigSky server.
  4. Buffered shots: In experiment scripts, use .constant() on any channel: 
    YAG_1_voltage.constant(value=1200)
YAG_1_lamps.constant(value=1)
YAG_1_shutter.constant(value=1)
YAG_1_qswitch.constant(value=1)
    Only channels with .constant() calls are sent during transition_to_buffered. The worker automatically orders them safely.
  5. Connection table: Already configured as a single line: 
    BigSkyHub(name='BigSkyLasers')
    Defaults: host="127.0.0.1", reqrep_port=55540, pubsub_port=55541, num_lasers=2, laser_prefix="YAG".

Patterns Observed

This is the third device using the RemoteControl/ExternalSoftware pattern:

#DeviceApproachChildrenWorker Override
1LaserLockDirect use of RemoteControlManual (4 channels)None
2RasteringDeviceSubclassManual (4 channels)Custom arm/disarm + raster step
3BigSkyHubSubclassAuto (28 channels)Safe command ordering

The subclass pattern is now well-established. Two variants have emerged for child creation: manual (flexible, explicit) and auto (concise, for fixed channel sets). The auto-creation approach is preferred when every instance of the device always has the same channels.

Future Work

  • Custom status indicators: BigSkyTab currently inherits only spinboxes from RemoteControlTab. If the BigSky GUI starts publishing status topics (e.g., interlock state, thermal alerts) via PUB-SUB, colored StatusIndicator widgets could be added following the RasteringTab pattern.
  • Per-laser enable/disable: Consider adding a top-level toggle to skip programming a specific laser during shots (e.g., if YAG_2 is offline for maintenance).
  • Backport auto-creation to RasteringDevice: RasteringDevice always has exactly X/Y output + X/Y monitor. Its connection table entry could be reduced to a single line.
