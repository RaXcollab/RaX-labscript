Bugs Found & Fixed

Bug 1 — exposure slider never reached the camera (67d44dd). Each slider's display-sync slot blocked the spinbox's signals (to break the slider↔spin feedback loop), so the camera was reached only via a separate, hand-duplicated slider→cam_thread.set_* lambda. fps and gamma had that lambda; exposure never did, so dragging the exposure slider moved the spinbox but left camera exposure unchanged. Not a regression — an omission since the file's creation (56d1733); verified deliberate-vs-bug by checking that camera.py coalesces fps/exposure/gamma identically via _pending, and timing-mode enables the exposure slider+spin together.
Root cause is the bug class: the H2 refactor replaced a single _building guard with per-widget blockSignals, which forced every slider to carry a hand-duplicated slider→physical formula (one in _*_slider_to_spin, one in the camera lambda). Exposure was just the first manifestation.
Bug 2 — "soft/User Home broken": single-axis moves & STOP logged nothing (419f02a). "Soft Home" was renamed "User Home"; HOME_SOFT is dead and KCube.soft_home() just calls hard_home(). The real defect is in User Home "Go X/Y": request_move_motor_axis tags single-axis moves move_motor_x_only / _y_only, but that pair was in neither _LOGGABLE_SUCCESS_TAGS nor _LOGGABLE_START_TAGS nor any _format_* branch. The motor did move (motor_x.move_to), but produced zero log output (silent start and success), while "Go Both" (tag move_motor, whitelisted) logged normally. The asymmetry was reported as a broken Home. A successful stop had the same omission — never acknowledged.

Key Decisions

Bug 1: Parity + kill the bug class (not symptom patch). Rather than add the one missing exposure lambda, the duplicated wiring was eliminated: one _bind_param_controls() wires display-sync and the camera commit together, so a slider's display sync can no longer exist without its camera path. Slider↔physical math lives only in _slider_to_phys/_phys_to_slider (single source of truth). Behavior preserved exactly (fps/gamma round 2, exposure raw; one camera call per gesture; blockSignals mirroring intact; gain/AOI untouched). Camera ref resolved lazily by name → wired once in _wire_signals, survives connect_to_camera_thread.
Bug 2: this whitelist-omission class has now bitten twice. Prior session's Bug B (backlash_* success-tag omission) and this session's move_motor_*_only / stop are the same defect class: a new request_* constructs a MotorCommand with a new tag, the action runs, but the tag is absent from the logging whitelists and _format_* branches, so it looks broken. Promoted to an auto-memory reference + a proposed structural rule (see Context Updates).

Recurring Bug Class

Logging-whitelist omission (2nd occurrence). Any new request_* that constructs a MotorCommand with a new tag MUST be added to BOTH _LOGGABLE_SUCCESS_TAGS and _LOGGABLE_START_TAGS (unless deliberately chatty-excluded, which must be documented) AND given a _format_start_message/_format_success_message branch. Otherwise the action executes but is silently unlogged and reads as a broken feature. Symptom is always observability, never motion — trace the data/log path, not the move call.
