Cutover Deployment

Full procedure in ~/.claude/plans/zmq-v2-cutover-playbook.md. Short form:

  1. Pre-flight: BLACS queue idle; all 4 GUIs closed; master/main clean on all 4 repos (operator edits to BaF_globals.h5/Closed_cell.py can remain unstaged).
  2. Merge per-repo with git merge --no-ff <topic-branch>. Order does NOT matter (Q4: no v1↔v2 negotiation). Push to origin.
  3. For rastering: merge from the worktree at GUIs/rastering-zmq-v2/, then optionally git worktree remove ../rastering-zmq-v2.
  4. Restart all 4 processes (BLACS + BigSky hub + HF_Locking + rastering GUI) before any new shot is queued. This is the atomic step.
Running mixed v1/v2 between BLACS and any single GUI yields immediate v1_protocol_refused errors on every CHECK_VALUE/PROGRAM_VALUE. There is no graceful degradation.

Rollback

If any smoke test fails: git revert -m 1 <merge-sha> on each repo (preserves the merge as a recorded rollback), push, restart all 4 processes again. Topic branches stay on origin so a fixed re-attempt is possible. Full procedure in the playbook.

What Changed for Daily Workflow

After merge + restart: nothing visible changes. All BLACS tabs behave identically. Setpoints program the same. Monitor values flow the same. Sequences compile and run the same.

The one user-facing difference: any external script (outside our 3 GUIs) that speaks v1 envelopes directly to a RemoteControl ZMQ port will get a v1_protocol_refused error. There are no known such scripts in this lab, but worth flagging if any ad-hoc tooling exists.

Architecture — Composition Pattern

Pre-coding audit by blacs-expert ruled out multi-inheritance (Qt + custom server base) due to MRO ambiguity around QObject. Instead, each GUI server composes the v2 base:

class BigSkyZmqServer(QtCore.QObject):
    def __init__(self, ...):
        super().__init__()
        self._v2 = _BigSkyV2Server(handlers=self._build_handlers(), ...)
        # _v2 owns the socket loop; this shell owns Qt signals

Same shape held across all 3 GUIs. The HF_Locking variant runs _v2 inside its existing QThread; BigSky and rastering run it as a daemon thread inside the GUI process. PUB-SUB on HF_Locking stays bare-integer (Q2 vs Q4 trade documented in the spec).

Patterns Observed

  • Cross-audit-then-execute — the pre-coding blacs-expert audit clarified composition-over-multi-inheritance, HF PUB-SUB shape, mock strategy, and HELLO emit-before-reply ordering. Zero rework on the initial PR scope.
  • Parallel reviewer pattern (4 agents, ~2 min wall time) — one fresh (non-fork) general-purpose reviewer per repo, post-push, pre-merge. Caught 1 Critical + 5 Important + several Minor. Reviewers also caught a false positive (rastering I1), which itself validates the pattern.
  • InMemoryTransport-based mock mini-server — deterministic test pattern that replaces real ZMQ sockets at the transport layer. Allows full request/reply flow + handler dispatch testing in-process. Pattern in userlib/external_gui_lib/zmq_v2.py; reused across 4 test suites.
  • Atomic cutover discipline — no master/main mutation across 4 repos until the operator says go. Topic branches + pre-merge code review + doc sync land before the human-in-the-loop step.
