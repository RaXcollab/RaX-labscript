LaserLock and Rastering BLACS Tab Redesign

Date: 2026-02-23  •  Commit: 73bbf2a  •  Context: Applied the custom tab pattern established in the BigSky redesign (see 2026-02-22_BigSky_tab_redesign.html) to LaserLockDevice (new) and RasteringDevice (rewritten).

What Changed

Two BLACS tabs were overhauled to replace generic spinbox layouts with purpose-built UIs. LaserLockDevice is a new device class (4 files) with per-laser group boxes pairing setpoint spinboxes with wavemeter readings, frequency error in MHz, and a lock quality indicator. RasteringDevice's initialise_GUI was fully rewritten to use paired X/Y coordinate rows with monitor labels alongside spinboxes, replacing the previous approach of calling super().initialise_GUI() and appending widgets. Both tabs follow the same override pattern established in the BigSky tab: create AO objects for all channels, build custom widgets, override _update_ao_widgets, _on_monitor_value_received, and _set_ao_widgets_enabled.

Key Decisions

New device class for LaserLock vs. in-tab detection

Alternative considered: keep RemoteControl as the device class and detect the laser lock case inside RemoteControlTab.initialise_GUI() based on child device names. Rejected because it would couple the base class to a specific device, and LaserLock has unique UI requirements (error computation, lock indicator) that don't generalize. A minimal subclass (12 lines in labscript_devices.py) is cleaner than conditional logic in the base class.

Shared connection IDs between outputs and monitors

LaserLock-specific issue: Output and monitor children share integer connection IDs (e.g., both Vexlum_Setpoint and Vexlum_Value use connection ID 3). If you call create_analog_outputs() for both outputs and monitors, the monitor AO objects overwrite the output AO objects in self._AO, breaking program_device.

Solution: Create AO objects for outputs only. Monitor values are displayed in custom QLabel widgets updated by _on_monitor_value_received, with no AO object backing. This works because monitors are read-only — they never participate in program_device or save/restore.

Full initialise_GUI override vs. super() + append

The RasteringDevice tab previously called super().initialise_GUI() to get the auto-generated spinbox layout, then appended the raster checkbox and status indicators below. This worked but put monitors in a separate section from their paired outputs, making the spatial relationship between X setpoint and X position unclear. The full override allows interleaving spinboxes and monitor labels in paired rows, matching the BigSky pattern. The cost is duplicating ~60 lines of boilerplate (connection table discovery, reconnect buttons, layout assembly), but this is the same code across all three tabs and could be extracted to a mixin in the future.

Patterns Observed

Shared initialise_GUI pattern now used across three tabs. All three custom tabs (BigSkyHub, LaserLockDevice, RasteringDevice) follow the same 14-step structure:
  1. Read connection table properties
  2. Create PubSub signal bridge
  3. Discover child devices (outputs vs. monitors)
  4. Create AO objects (outputs; monitors only if IDs don't collide)
  5. Create standard widgets for continuous outputs only
  6. Build custom content layout (device-specific)
  7. Create reconnect buttons
  8. Assemble layout with DynamicStackedWidget
  9. Set ao_toolpalette_widget/am_toolpalette_widget aliases
  10. Add Disable Input checkbox
  11. Hide initially (shown after connection)
  12. Add failure button
Steps 1-4 and 7-12 are identical across all three. Only step 5-6 (custom content) differs. This is a strong candidate for a base class refactor or mixin.
Three override methods form the custom tab API. Every custom tab overrides exactly these three methods from RemoteControlTab:
  • _update_ao_widgets(remote_values) — called by check_remote_values poll to update spinboxes/widgets from remote state
  • _on_monitor_value_received(connection, value_str) — called by PUB-SUB subscriber to update monitor labels/indicators
  • _set_ao_widgets_enabled(enabled) — called by Disable Input checkbox and connection status to enable/disable interactive controls
This is a stable API. Future device tabs only need to implement these three methods plus their custom content layout.

Future Work

  • Extract shared initialise_GUI boilerplate into a mixin — Steps 1-4 and 7-12 are identical across BigSkyHub, LaserLockDevice, and RasteringDevice. A CustomTabMixin with a _build_custom_content() hook would eliminate ~60 lines of duplication per tab.
  • LaserLock: add _recently_changed cooldown — Currently not needed (setpoint spinboxes don't visibly flicker on poll revert), but should be added for consistency if the tab gets toggle-style controls in the future.
  • LaserLock: configurable lock threshold — Currently hardcoded at 100 MHz (_LOCK_THRESHOLD_MHZ). Could be made a connection table property or a per-laser setting if different lasers have different linewidths.
  • RasteringDevice: consider _recently_changed — Same poll-revert race applies to spinboxes, but the visual flicker is minor. May become more visible if coordinate precision increases.
