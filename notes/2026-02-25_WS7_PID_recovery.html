WS7 Wavemeter PID Config Recovery & BLACS Startup Protection

Date: 2026-02-25  •  Commit: pending  •  Context: PC restart lost wavemeter PID settings; BLACS blindly overwrote saved setpoints with zeros from the restarted GUI

What Changed

After a PC restart, the HF_Locking GUI came up with zeroed frequency setpoints (the WS7 DLL does not persist PID settings set at runtime). BLACS's _fetch_initial_values blindly accepted these zeros and overwrote its saved state, which still had the correct setpoints (348.661086 / 420.899794 THz). A new override in LaserLockTab now detects mismatches between remote and saved values on startup and prompts the user to choose which to keep. The user can push saved values back to the remote server or accept the remote state.

Separately, a context file was written for a future session to implement full PID config persistence in the HF_Locking GUI itself, and the CLAUDE.md External GUI Registry was corrected.

Bugs Found & Fixed

Bug: BLACS startup overwrites good setpoints with zeros.
The base RemoteControlTab._fetch_initial_values unconditionally accepts whatever the remote server reports and updates the front panel. After a PC restart, the HF_Locking GUI has no persistence and reports 0.000000 THz for all channels. BLACS then overwrites its saved 348.661086 / 420.899794 THz with zeros. The new override compares remote vs saved values (threshold: 0.01 MHz = 1e-8 THz) and shows a dialog on mismatch.
Root cause: WS7 DLL does not persist PID settings set at runtime.
The WS7 native app stores config in wlm_ws7.ini (via Windows VirtualStore at C:\Users\radmo\AppData\Local\VirtualStore\Program Files (x86)\HighFinesse\...), but PID gains set via SetPIDSetting() at runtime are NOT written to this file. After a restart, the WS7 reverts to factory/INI defaults. The HF_Locking Python GUI adds no persistence layer on top. This is the upstream root cause; the BLACS override is a downstream safety net.

Key Decisions

  1. Dialog-based user choice, not auto-restore. Auto-restoring saved values would be dangerous if the user intentionally changed setpoints in the WS7 native app while BLACS was off. The dialog shows exact deltas in MHz so the user can make an informed decision.
  2. Threshold of 0.01 MHz (1e-8 THz). Filters floating-point representation noise while catching any real setpoint drift. Typical setpoint changes are tens of MHz or more.
  3. "Use saved" triggers program_device(). This pushes the saved values back through the full program_manual path, which sends them to the remote server via ZMQ. This is the same code path as a user manually changing a spinbox value.
  4. Two-layer fix strategy. The BLACS override (implemented now) is the safety net. Full PID persistence in the HF_Locking GUI (documented in pid-persistence.md for a future session) is the proper fix that eliminates the problem at the source.

How to Use

  1. Start the HF_Locking GUI as normal.
  2. Start BLACS. During the LaserLock tab initialization, _fetch_initial_values runs.
  3. If remote setpoints match saved state (within 0.01 MHz): no dialog, silent accept.
  4. If mismatch detected: a dialog appears showing each mismatched channel with saved value, remote value, and delta in MHz.
  5. Click Yes to keep saved values and push them to the remote server. Click No to accept the remote values.

Example dialog text

The remote laser lock GUI has different frequency setpoints
than the saved BLACS state.
