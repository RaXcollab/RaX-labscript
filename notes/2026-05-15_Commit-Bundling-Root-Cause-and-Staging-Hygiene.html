Question

Why did b328f9f bundle two logically separate changes when only one — Task 12 Step 3, “snapshot from live _pubsub_cache in transition_to_buffered” — was intended for that commit?

Root Cause

A prior session left an uncommitted deletion of the redundant RasteringWorker.post_experiment override in userlib/user_devices/RasteringDevice/blacs_workers.py. The current session then ran git add <file> for the Step 3 edit. git add on a path stages every uncommitted hunk in that file — so the prior-session deletion and the new Step 3 edit were fused into a single commit.

Functional Assessment

ConcernVerdict
Is the bundled post_experiment deletion correct? Yes — the override was redundant; base RemoteControlWorker.post_experiment already performs the snapshot via _pubsub_cache. The deletion is explicitly permitted by the refactor plan.
Did removing the override leave dead imports? No — transition_to_buffered step 2 still uses import h5py; nothing became unused.
Net effect of the bundle Two correct, related changes in one commit. No functional defect; only a commit-granularity / message-accuracy concern.

Resolution

Chosen resolution: amend the commit message (not split, not revert). The message already documents both changes: “Rastering: snapshot from live drain cache; remove redundant post_experiment override (base RemoteControlWorker handles it)”. This resolution is already satisfied — no further git action.
Do not re-amend b328f9f. It is buried under later commits (HEAD = d974676). Amending it would require an interactive rebase rewriting every subsequent SHA — destructive, unnecessary, and pushing is forbidden regardless. The existing message is accurate; leave history intact.

Generalizable Lesson

In a mixed working tree, git add <file> stages ALL uncommitted hunks in that file — including changes from prior sessions you did not author this session. Before every commit, inspect git diff --cached and confirm it contains only the intended hunks. When the tree is known to be mixed, stage at hunk granularity with git add -p. The existing memory note “Mixed working tree is normal” states the situation but not this staging-semantics hazard or the --cached guard; both are now captured in feedback_git-staging-mixed-tree.md.
