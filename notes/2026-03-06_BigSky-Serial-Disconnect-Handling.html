BigSky YAG: Graceful Serial Disconnect Handling

Date: 2026-03-06  •  Commit: 0a3abb9 (GUIs/BigSkyControl)  •  Context: Serial disconnect caused infinite error spam and stale PUB-SUB values hiding the failure from BLACS

What Changed

When the BigSky YAG laser's USB-serial connection dropped, the GUI entered an infinite loop of >cg polls producing "Temperature parse error" spam. The ZMQ PUB-SUB server kept broadcasting stale cached values, so the BLACS tab never showed the laser as offline. This session added a _sendCommand() gateway that detects disconnects (SerialException, OSError, or 3 consecutive empty/decode errors), resets all cached hardware state, and starts a 5-second reconnect timer. The ZMQ layer now checks isConnected() before broadcasting or dispatching commands, so BLACS correctly triggers its 30s stale timeout.

Key Decisions

  • 3-strike consecutive error threshold rather than single-error disconnect. Serial lines are noisy; a single garbled response shouldn't trigger full disconnect. Three consecutive empty or decode-error responses is a reliable indicator.
  • PUB-SUB silence (not error broadcast) for disconnect. When disconnected, the PUB loop simply skips the laser. BLACS already has a 30s stale timeout that handles this gracefully. Broadcasting an explicit "disconnected" value would require protocol changes in the BLACS tab.
  • Qt main thread for all reconnect logic. Both the reconnect timer and the disconnect handler run on the Qt main thread, eliminating race conditions between disconnect detection and reconnect attempts.
  • Full state reset on disconnect. _handleDisconnect() clears active, shutter, qswitch, and mode caches. Without this, a reconnect could leave compound operations (like warmup) in an inconsistent state.

Architecture

Serial I/O Flow (after refactor):

  Any command ──> _sendCommand(cmd_bytes) ──> serial.write/readline
                        │                           │
                   catch exception              3 empty responses
                        │                           │
                        └─────── _handleDisconnect() ──> reset state
                                       │                    stop warmup
                                       │                    close port
                                       │                    start 5s timer
                                       v
                              _attemptReconnect() ──> probe with >cg
                                       │
                                  success? ──> _handleReconnect()
                                       │          re-query all state
                                  failure? ──> reschedule 5s timer

ZMQ Propagation:

  PUB-SUB loop:  if ctrl.isConnected() → publish   (else skip → BLACS stale timeout)
  REQ-REP:       if ctrl.isConnected() → dispatch  (else return error string)
Thread safety note: isConnected() reads a Python bool from the ZMQ thread. This is GIL-atomic and safe without locking. The bool is only written on the Qt main thread.

Bugs Found & Fixed

Temperature parse crash on garbled data. Before this session, any non-numeric response to >cg would crash the temperature parse with an unhandled ValueError. Now all float/int casts are wrapped in try/except.
