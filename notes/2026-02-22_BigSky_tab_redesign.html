BigSky YAG BLACS Tab Redesign and Bug Fixes

Date: 2026-02-22  •  Commits: 434c49d (CHECK_VALUE fix), 71fe48f (UI redesign + bug fixes), e42e198 (BigSkyControl radio sync)  •  Context: Replaced generic spinbox BLACS tab with purpose-built UI; discovered and fixed three interacting bugs in the BLACS base class program_manual / check_remote_values pipeline.

What Changed

The BigSkyHub BLACS tab was rewritten from the default auto-generated spinbox layout to a per-laser group box UI with toggle buttons, combo boxes, and color-coded monitor indicators. During testing, three bugs were found and fixed: a CHECK_VALUE crash (server didn't support all channels), a toggle-revert race condition (periodic poll overwrites user input), and silent mode-change rejection (program_manual re-sends unchanged values that block the intended change). The BigSky GUI itself was also patched to sync radio buttons when modes are changed remotely.

Bugs Found & Fixed

Bug 1: CHECK_VALUE crash (commit 434c49d)

Symptom: BLACS tab crashes on startup when check_remote_values queries channels the BigSky server doesn't support.
Root cause: The base class iterates ALL connections; BigSky has command-only channels (warmup, start_lasing, stop) and per-laser channels that may not exist if the laser isn't launched in the GUI.
Fix: Override check_remote_values, check_all_remote_values, and program_manual in the worker to skip command channels and gracefully handle unregistered lasers.

Bug 2: Toggle buttons revert after click (commit 71fe48f)

Symptom: User clicks a toggle button (e.g., Lamps ON). Button turns green, then snaps back to gray within 1-5 seconds.
Root cause: Race condition between user input and the periodic check_remote_values poll (every 5s). Sequence:
  1. User clicks toggle → AO value set → program_device queued in state machine
  2. Meanwhile, a pending check_remote_values result returns the OLD value
  3. _update_ao_widgets overwrites the AO object with the old value → toggle reverts
  4. program_device may then run with the reverted value, undoing the user's action on hardware
Fix: _recently_changed dict with time.monotonic() timestamps. _update_ao_widgets skips any channel changed within the last 10 seconds.

Bug 3: Lamp mode changes silently rejected (commit 71fe48f)

Symptom: User selects "External" from lamp mode combo while lamps are running. BLACS shows no error, but mode doesn't change on the BigSky controller.
Root cause: program_manual sends ALL front panel values every time ANY control changes (BLACS base class behavior). When the user changes lamp_mode, program_manual also re-sends lamps=1 (current state). BigSky GUI's _remoteSetLampMode checks self.activeStatus and rejects mode changes while the laser is active. The done_event.set() is in a finally block, so the rejection returns SUCCESS to BLACS.
Fix (BLACS side): _last_sent_values tracking in the worker. program_manual only sends values that actually changed from the last known state. check_remote_values seeds the tracking dict.
Fix (GUI side): Mode combo is interlocked — disabled when lamps are active, mirroring the BigSky controller's own constraint. Also, radio buttons in BigSkyControl now update when modes are set via ZMQ.

Key Decisions

Custom widgets vs. auto-generated spinboxes

The default auto_create_widgets() gives every AO a spinbox. For a laser controller, binary controls (lamps on/off, shutter open/close) need toggle buttons, mode selectors need combo boxes, and monitors need color-coded indicators. Decision: call create_analog_outputs() for ALL channels (BLACS needs the AO objects for save/restore and program_device), but only create standard widgets for continuous values (voltage). Binary, mode, and hidden channels get custom widgets or no widget at all.

Delta-only programming at worker level, not tab level

The _last_sent_values filter was placed in the worker's program_manual rather than the tab's _program_device_wrapper. Reason: the worker is the single point of truth for what was actually sent to hardware. The tab can't reliably know what the worker sent, especially across restarts (save/restore loads old values).

10-second cooldown for recently-changed guard

Chosen to be 2x the check_remote_values poll interval (5s). This ensures at least one full poll cycle completes before the guard expires, so the remote value will have caught up to the user's change by the time the guard drops.

Patterns Observed

Three recurring BLACS base class friction points for RemoteControl devices:
  1. Full-dict programming: program_manual sends all AO values on any change. For devices with ordering constraints or side effects, this causes unintended state changes. Workaround: _last_sent_values delta tracking in the worker.
  2. Poll-vs-input race: check_remote_values poll overwrites AO objects with stale values. Subtle with spinboxes, very visible with toggle buttons. Workaround: _recently_changed cooldown dict in the tab.
  3. Manual vs. buffered asymmetry: transition_to_buffered uses safe ordering (COMMAND_ORDER), but program_manual iterates connections in registration order. Ordering constraints only enforced during shot execution, not manual front panel interaction.
These are base class behaviors in blacs/blacs/device_base_class.py. They affect any RemoteControl-pattern device with ordering constraints or binary/toggle UI. The workaround patterns should be reused in future device classes.
BigSky ZMQ server silently swallows command failures. The done_event.set() is in a finally block, so rejected commands return SUCCESS. BLACS has no way to detect the failure. Mitigation: prevent invalid commands from being sent (interlocking, delta-only sending) rather than relying on error detection.

Future Work

  • Apply toggle/combo pattern to RasteringDevice tab — currently uses default spinbox layout. Binary controls (enable/disable) and mode selectors would benefit from the same treatment.
  • Investigate LaserLock tab — if it has binary controls, apply the same pattern.
  • BigSky ZMQ error reporting — modify the BigSky GUI server to return actual success/failure in the response payload instead of always returning SUCCESS. Would allow BLACS to detect and report rejected commands.
  • Consider upstreaming delta-only program_manual — the _last_sent_values pattern could be useful in the RemoteControl base class. Would require careful testing with devices that rely on re-sending values.
  • Multi-laser testing — num_lasers changed to 1 for current setup. When second laser is connected, test that per-laser group boxes render correctly and unregistered-laser handling still works.
