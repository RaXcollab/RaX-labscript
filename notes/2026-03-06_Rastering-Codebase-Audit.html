Rastering Codebase Architectural Audit

Date: 2026-03-06  •  Commit: pending  •  Context: Full audit of rastering GUI + BLACS device, research, cross-audit, implementation of surviving fixes

What Changed

Conducted a full architectural audit of the rastering codebase (~4,000 lines GUI + ~536 lines BLACS device). Researched galvo/laser scanning patterns, PyQt hardware control, and ZMQ instrument patterns. Cross-audited all findings with blacs-expert, which rejected 3 recommendations (ZMQ extraction, discoverable topics, QThread modernization). Implemented 7 fixes across 4 files + 1 new file, spanning both rastering-gui and labscript-suite repos.

Key finding: The architecture is fundamentally sound. Single-owner motor thread, priority queue, PUB-SUB cache, affine calibration with degeneracy checks -- all validated. No major rewrites needed.

Key Decisions

  • Rejected ZMQ server extraction -- ZMQ is only 15% of SystemController. Extraction would require passing controller reference back (defeating the purpose) or building a formal status-snapshot API. "God class" label was overstated.
  • Rejected discoverable STATUS_TOPICS -- subscribing to "" receives heartbeat + monitor messages, causing spurious processing. Each topic requires its own handler code anyway.
  • Rejected QThread modernization -- current QThread subclass is correct for single-loop workers like the camera thread. moveToThread is preferred for event-driven QObjects, not run-loops.
  • MOVE excluded from _read_and_cache_position() -- MOVE intentionally sets _last_target_xy to the commanded target, not readback position. Helper only applies to READ_POS and HOME commands.
  • blockSignals() over _building flag -- Qt's native mechanism, exception-safe, scoped per-widget. No try/finally needed since setValue() doesn't raise.

Bugs Found & Fixed

H1: Camera thread-safety bug. QTimer.singleShot(2000, _apply_extras) in _load_ini_file() called apply_ini_to_camera(cam, path) directly from the GUI thread while the camera thread was actively calling cam.grab(). The uEye API is not thread-safe. Fixed by routing through the camera thread's existing _pending dict + QMutex pattern.
M6: Calibration read outside lock. self.calibration was read outside _state_lock in the ZMQ status publishing loop while the GUI thread could be updating it. Moved inside the existing lock scope.

Audit Validated Architecture

The following design choices were explicitly confirmed correct by blacs-expert:

  • Sequential motor moves (X then Y) -- correct for independent KCube USB devices; simultaneous would require two threads
  • QTimer.singleShot() raster chaining -- standard Qt pattern, already hardened with _state_lock covering check + next(it) + enqueue
  • Shared pubsub_monitor_cache dict -- safe under GIL; written by GUI thread signal slot, read by worker via dict() copy
  • @define_state(MODE_MANUAL, True) on raster checkbox -- toggles during buffered mode are queued correctly
  • Pure raster_paths.py -- no Qt/hardware imports, deterministic, testable
  • Frozen dataclass config -- single source of truth, immutable
