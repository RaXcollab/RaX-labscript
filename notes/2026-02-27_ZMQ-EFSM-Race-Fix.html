Fix ZMQ EFSM Race in NI_DAQmx Acquisition Worker

Date: 2026-02-27  •  Commit: pending  •  Context: Fix intermittent ZMQ "Operation cannot be accomplished in current state" crash in 6361 acquisition worker

What Changed

The NI_DAQmx acquisition worker's real-time plotting code shares a ZMQ REQ socket (data_socket) between the BLACS worker thread and a DAQmx read callback thread. The callback thread (read(), line 590) sends manual-mode data on this socket inside tasklock. However, the worker thread's transition_to_buffered used the same socket before stopping the manual-mode task, creating a window where both threads could interleave REQ send/recv pairs. ZMQ REQ sockets are strict state machines (send-recv-send-recv); any interleaving puts the socket into an unrecoverable EFSM error state.

The fix has two parts: (1) move stop_task() before any socket usage so the callback thread is guaranteed stopped, and (2) wrap all remaining data_socket operations with tasklock for defense-in-depth.

Bugs Found & Fixed

ZMQ EFSM race condition (intermittent crash)
Symptom: zmq.error.ZMQError: Operation cannot be accomplished in current state during transition_to_buffered on the 6361 acquisition worker. Intermittent — depends on callback timing.
Root cause: data_socket (ZMQ REQ) shared between two threads without synchronization. The DAQmx read() callback (line 590) sends manual-mode plotting data on the socket inside tasklock, but transition_to_buffered used the socket before calling stop_task() and without holding tasklock. If the callback fires between the worker's send and recv, the REQ state machine breaks.
Fix: (1) Call stop_task() first to guarantee the callback thread is dead. (2) Wrap socket operations with tasklock for defense-in-depth.
Latent bug in transition_to_manual non-abort path
The non-abort branch of transition_to_manual also used data_socket without holding tasklock. While less likely to trigger (manual-mode task is already stopped by post_experiment), it was still unprotected. Now wrapped with tasklock.

Key Decisions

Why both stop_task() reorder AND tasklock? Stopping the task first is the primary fix — it eliminates the race by ensuring the callback thread is not running. The tasklock wrapping is defense-in-depth: if a future change introduces another concurrent path, the lock prevents socket corruption. Belt and suspenders for a Heisenbug that would otherwise be very difficult to reproduce and diagnose.

Patterns Observed

ZMQ REQ socket state machine fragility: REQ sockets enforce strict send-recv alternation. Any shared usage across threads without serialization will eventually hit EFSM. This is a known ZMQ footgun. The existing _reset_data_socket() pattern (used in the abort path) destroys and recreates the socket as a recovery mechanism, but prevention via locking is preferable to recovery via reset.
DAQmx callback threading: NI DAQmx EveryNSamplesEvent callbacks run in a separate thread managed by the DAQmx driver, not a Python thread. Any shared state accessed by these callbacks must be explicitly synchronized. The existing tasklock was already used for self.task and self.read_array access in the callback but was missing for data_socket outside the callback.

Future Work

  • The read() callback's manual-mode socket send (line 620) is inside tasklock but could block if the real-time plotting server is slow to respond. Consider a non-blocking send pattern or DEALER socket if this becomes a bottleneck.
  • The abort path uses _reset_data_socket() which destroys/recreates the socket. This is correct for abort recovery but could be unified with the locking pattern for consistency.
