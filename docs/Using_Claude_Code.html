Using Claude Code with Labscript

Last updated: 2026-02-21  •  Version: 2.0  •  Canonical reference for the RaX lab Claude Code setup

What is Claude Code?

Claude Code is an AI coding assistant that runs in a terminal (or VS Code extension). It can read files, edit code, run commands, and search the codebase. We have it configured with project-specific knowledge about our labscript-suite setup so it can help with debugging, writing new device classes, and understanding the codebase.

How to Launch

Open a terminal in the labscript-suite folder and run claude. Or use the Claude Code VS Code extension (Ctrl+L to open the chat panel).

What Claude Code Already Knows

Every session, Claude automatically reads CLAUDE.md in the repo root. This gives it:

  • Multi-repo structure (labscript-suite = user-facing, blacs/ / labscript-devices/ / labscript-utils/ = separate backend repos)
  • Where custom devices live (userlib/user_devices/)
  • Key coding conventions (e.g., use inmain() not qtlock for Qt widget calls in BLACS tabs)
  • Log file locations (logs/BLACS.log, logs/BLACS_faulthandler.log)
  • How to activate the conda environment
  • The ExternalSoftware/RemoteControl communication pattern (REQ-REP + PUB-SUB)

You do not need to re-explain the repo layout or conventions at the start of each session. If Claude seems confused about the project structure, just say "read CLAUDE.md."

Tips

  • Be specific about what you want. "Fix the bug" is worse than "the RemoteControlTab crashes when I click reconnect."
  • Claude can read the Confluence PDF. Say "check the Confluence PDF for how ExternalSoftware communication works" and it will extract the relevant pages.
  • It knows about separate repos. If you need to commit, say "commit this to labscript-devices" and it will commit to the right repo. Always say "don't push" if you want to review first.
  • Plan mode. For bigger tasks, Claude enters "plan mode" where it explores the codebase and proposes a plan before making changes. You approve the plan before any code is written.
  • Context gets compacted in long sessions. If Claude seems to forget earlier context, this is normal. The CLAUDE.md and agent prompts ensure key knowledge persists regardless.
  • Propose defaults, don't ask open-ended questions. If Claude is asking too many questions, tell it: "propose a default and I'll correct you."
  • Front-load the key decision. For multi-file changes, Claude should present a plan first. If it doesn't, ask for one.
  • Explore code first. Many answers are already in the codebase. Claude should check before asking you.

BLACS Communication Contract

Full document: userlib/user_devices/BLACS_COMMUNICATION_CONTRACT.md. Summary:

ProtocolFormatPurpose
ZMQ REQ-REP {"action": "HELLO|PROGRAM_VALUE|CHECK_VALUE", "connection": str, "value": any} Synchronous control: set values, read values, connection check
ZMQ PUB-SUB "{topic} {value}" (space-separated string) Async monitoring: heartbeat (~1 Hz), positions (~4 Hz), status (~1 Hz)

Integration Checklist

Adding a new external GUI to BLACS:

  1. Start session-notes to track decisions throughout the integration.
  2. Decide: subclass RemoteControl or use it directly?
  3. Check for local agents: look in the external GUI folder for .claude/agents/. Use local agents for domain questions, device-builder for BLACS-side architecture.
  4. External GUI side: add ZMQ server (HELLO, PROGRAM_VALUE, CHECK_VALUE + optional PUB-SUB). Follow BLACS_COMMUNICATION_CONTRACT.md.
  5. Create device class (if subclassing): 5 files in userlib/user_devices/{DeviceName}/.
  6. Connection table entry: import, instantiate, add children.
  7. Test: start GUI first, then BLACS. Verify REQ-REP + PUB-SUB + buffered mode. Use diagnostics if errors appear.
  8. Update registry: add to External GUI Registry in CLAUDE.md.
  9. Wrap up: resume session-notes for commit message, HTML lab note, context updates, and introspection.
